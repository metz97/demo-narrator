## 3. Section 2 — Item 76469: Projects → Browse → Categories *(backlog #9)*

### 3.1 — The problem

**[SAY]**
> Last item, and this one's a bit different — it's the **Browse Categories** experience.

> The problem was that our classifications were completely **flat**. Every classification was shown as one long list of names, with no parent-child relationship — even though the underlying data already had level and parent fields.

> So as part of this, we've moved LCA to read from the **Source classifications index** instead of our own LCA index. That index already has the full hierarchy, and it already has **translations for other languages** — which is going to save us a lot of work when we do internationalisation for LCA. We've also removed the old LCA lambda that was writing to the old index, and retired that index.

### 3.2 — Browse landing page

**[DO]** Switch to the Browse Categories tab.

**[SAY]**
> Here's the landing page. Each **root category** is now a clickable **tile**, showing the category name and a count.

**[SAY]**
> That count is important — it's an **aggregate**. So "Structure (93)" means 93 items across that category **and everything nested underneath it**, not just items tagged directly at the top level. And it updates on the next load when the data changes — no manual cache clear needed.

**[SAY]**

### 3.3 — Full classifications list with hierarchy

**[DO]** Navigate to the full classifications list.

**[SAY]**
> This is the full list, and this is where the hierarchy really shows. Classifications are now **grouped under their top-level parent**, and children are **indented underneath** their parent.

> And that nesting works at **any depth** — third level, fourth level, it doesn't matter. It's not hard-coded to two levels. A classification with no children just renders as a plain list item, with no expand affordance.

**[DO]** Type a query into the search box on that page.

**[SAY]**
> The search on this page now searches **at any depth**, not just root names. And when it returns a match, it shows you the **ancestor path** with it — so you get context like "Metal panels, then Aluminium sheet panels", and you know where in the tree you actually are.
